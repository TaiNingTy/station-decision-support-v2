# Miami 空间连接审查

审查日期：2026-09-14。范围：`data/miami/2026-09-14/`、空间连接脚本、上游站点主表脚本及其说明。原始数据、结果、脚本均未修改；所有执行与故障模拟在临时副本中进行。本目录只新增审查记录。

**结论：现有几何计算可以保留，适合作为第一版站点法定分区画像；正式接入人口、就业和AI前，应修复结果发布与版本记录问题，并补齐逐环带证据及非排他覆盖的语义。** 现有 `PASS` 只表示脚本列出的几何／输入检查通过，不代表整个V2输入包验收完成。

## 已确认正确的部分

- 三个环带以英制参数定义：0–660、660–1,320、1,320–2,640 ft；米制计算半径为精确换算结果。
- EPSG:26917、`always_xy=True`、`quad_segs=64` 与记录的环境一致；展示面积换算正确。
- 21站、63个不重叠环带，另有21个半英里累计圆。裁切后求并集，同码先合并；原始分区代码保留，没有工业区排除或伪造人口需求。
- 独立计算与保存的面积、占比和计数一致。最大面积差约0.0000005 m²，属于六位小数输出的舍入量级；不是关于源数据精度的结论。
- 235个多边形对账：146个至少有正面积交集、89个未命中任何半英里圆；112个被多个站命中。
- 21站最大范围均在查询窗口内，最小余量为 **1,414.17 ft**，在 Bayfront Park。
- 当前文件哈希全部匹配；在原环境的副本中重跑，JSON/GeoJSON未发生字节变化。未登记的输入坐标变化会触发停止，并且该输入哈希失败路径没有继续写出结果。
- 两个无效源几何FID 182、983经修复后，235个投影后的多边形均有效。本次两项修复的投影面积诊断没有实质变化，未发现当前修复造成可见面积损失。

## 需要修复的实现问题

### F1 · P1：最终校验失败仍写出结果，并标记DONE

位置：[结果发布与readiness更新](../../scripts/build_miami_station_zoning_profile.py:241)。

脚本先写画像、几何、校验报告、readiness和manifest，最后才依据 `val.status` 返回退出码。`station_spatial_join_status` 无条件写成 `DONE`。

在隔离副本中，向最终校验状态注入 `FAIL`，程序退出码为1，但仍写入失败校验文件、更新manifest，并把readiness标为DONE。当前真实数据的校验仍是PASS；此测试验证的是失败处理路径。

**影响：** 下游若按文件存在或DONE加载，可能读到未通过最终校验的结果；上一版有效结果也会被覆盖。仅靠进程退出码不能保护静态网页读取链。

**建议：** 先在临时目录生成并完成全部校验；通过后再发布整套结果。失败日志另存，不覆盖上一版成功产物。区分 `build_status`、`geometry_validation_status` 和 `ready_for_downstream`，不要将“计算结束”和“可供下游使用”混为一个DONE。

### F2 · P2：脚本修改后，manifest可能继续记录旧代码哈希

位置：[脚本哈希登记](../../scripts/build_miami_station_zoning_profile.py:266)。

代码仅在脚本路径尚未出现在inputs时追加哈希；已有记录不会更新或拒绝不匹配。隔离副本仅追加一行注释后重跑，程序PASS，但manifest中的脚本哈希与实际运行文件不一致。

**影响：** 后续正常改算法、修缺陷或调参数后，结果可能被归到旧程序版本，破坏“哪个版本生成哪个数字”的证据链。

**建议：** 为每次构建保存实际脚本哈希和参数哈希。采用冻结构建则遇到变化停止并建立新版本；采用更新构建则准确更新当前哈希并保留旧manifest。不要静默保留旧值。

### F3 · P2：重跑上游站点脚本会清掉空间连接元信息，却保留空间结果

位置：[上游readiness重建](../../scripts/build_miami_station_master.py:145)、[上游manifest重建](../../scripts/build_miami_station_master.py:172)。

按README中给出的上游命令，在副本中正常重跑后：readiness回到NOT_RUN；manifest的 `spatial_join_build` 和空间脚本哈希消失；旧空间画像、校验报告和环带文件仍被目录通配符收集进outputs。

**影响：** 会出现“空间结果文件仍在、空间过程信息消失、状态变为未执行”的混合包。未来上游真正变化时，更难分辨哪些下游结果已经过期。

**建议：** 每个阶段拥有自己的manifest与输出清单；下游记录准确的上游版本。上游变化时明确将下游标记为STALE，或由统一构建入口按顺序重算。上游脚本不要把目录中所有历史JSON都当作本次输出。

## 接入人口、就业及AI前的升级

### U1 · 覆盖比例不是分配权重；补全网去重几何

位置：[逐多边形比例](../../scripts/build_miami_station_zoning_profile.py:205)、[README“分摊”表述](../../data/miami/2026-09-14/README.md:92)。

当前 `share_of_polygon_by_station` = 某站半英里圆覆盖的多边形面积 / 原多边形面积，是**允许重叠的覆盖比例**，并未完成需求分配。235个多边形中有94个的各站比例合计大于1；FID 98合计约12.1674，FID 1117合计11。

**独立核算的面积证据：** 21个半英里圆逐站面积相加约 **16.49 square miles**，实际全网并集只有 **3.57 square miles**，前者约为后者4.62倍。这是面积重复，不意味着人口或需求一定恰好高估4.62倍。

当前160对相交面积可用于查看站间关系，不能靠“面积总和减去所有两两交集”获得全网去重值，因为存在三站及更多站共同覆盖；在这份数据上这样做会得到负面积。

**建议：** 文档改为“非排他覆盖比例”；结构中加入 `is_allocation_weight:false`。输出半英里范围的全网并集几何与面积。人口／就业需求分配另建规则，明确未分配比例、换乘角色和竞争关系，不能把覆盖比例直接作为权重，也不应机械归一化后宣称得到真实选择概率。

### U2 · 逐环带、逐数字的FID证据尚未保存

位置：[聚合输出](../../scripts/build_miami_station_zoning_profile.py:142)、[逐环带丢弃贡献表](../../scripts/build_miami_station_zoning_profile.py:176)。

`band_metrics`计算了逐FID的裁切面积，但环带调用中的第二个返回值被丢弃。画像仅保存每代码面积、占比及FID数量。`station_overlap.json`保留的是0–½ mile累计圆对应的FID，不能直接回答“这个¼–½ mile环带的某个比例由哪几个FID贡献”。

**建议：** 新增贡献明细，至少包含 `station_id / band_id / source_snapshot / FID / M21_ZONE / clipped_area / geometry_id`，同时保留同码并集方法；各FID面积之和可能有重叠，不能替代并集结果。网页按明细高亮来源，AI引用应指向证据ID而非自行补写来源。无需把庞大几何全部塞进LLM上下文，可按证据ID读取。

### U3 · 依赖“记录”不等于环境“锁定”；坐标转换说明应来自实际操作

位置：[默认选择转换与固定说明](../../scripts/build_miami_station_zoning_profile.py:70)、[版本说明](../../data/miami/2026-09-14/README.md:117)。

目前运行版本记录完整，但没有GIS依赖锁文件或统一运行入口。本机默认 `python3` 为3.14且没有Shapely/pyproj；已成功复算的环境是 `/opt/anaconda3/bin/python3.13`，Python 3.13.9、Shapely 2.1.2、GEOS 3.13.1、pyproj 3.8.0、PROJ 9.8.1。README的通用python3命令只运行上游站点脚本，不能复算空间连接全流程。

`grid_used=False`与“固定4 m、无实质影响”的说明是代码写死的，转换本身却由pyproj默认选择。当前环境中的实际操作与记录一致；换环境、投影或网格可用性后，不应自动继承这段说明。

**建议：** 提供锁定依赖及明确的构建命令；记录实际选用的坐标转换操作、数据库/网格信息，必要时校验是否符合指定策略。4 m约13.12 ft是转换操作报告的精度，不是GTFS点、源分区边界或整个模型的总精度，也不是结果“无影响”的证明。

### U4 · 几何质量、空间语义与展示精度需要分层

- FID 182/983的修复诊断目前记录deg²。虽然正式面积计算没有使用这些值，但质量报告应补充投影面积诊断、修复方法及修复后／投影后的有效性结果；不能仅以“非空”代表几何已通过检查。
- `code_conflict_area_m2`目前计算的是“各代码并集面积之和 − 所有代码并集面积”，属于重复计入量；当三个代码覆盖同一空间时不等于实际冲突区域面积。本次数据上的差异主要在舍入量级，未造成当前宏观结论改变。建议改名为excess，或另用异码相交几何的并集计算真正的冲突范围。
- 单环带内最小裁切碎片约 **9.43 sq ft**；School Board内环的D2合计约 **25.52 sq ft**。保留它们有利于审计，但AI不应据此宣称站点具有显著工业服务需求。记录面积占比和位置敏感性，展示适当舍入；不要把六位小数当成真实测量精度。
- 画像JSON主要通过config字符串说明欧氏代理，GeoJSON才有明确的布尔标志。面向AI的数据包应显式携带 `catchment_type`、`is_validated_walk_catchment:false`、`demand_origin_or_destination:TO_BE_EVALUATED`、`is_population_allocation_weight:false`，避免单独传递一段band对象后丢失语义。
- 如果仍需实现此前提出的“站点参考点落在哪个zoning”子任务，应单独输出点匹配状态。本次只读检查发现 **Freedom Tower与Brickell参考点没有被任何源zoning多边形覆盖**，其余19点有匹配。这不会使周边环带画像失效，也不能据此断言站点不合法或无需求；不应强制最近邻补值。
- 旧readiness中的 `walk_network.distance_proxy_m=1200`属于未执行的步行分析设想，与本轮英制环带不是同一参数。应明确阶段和适用范围，防止后续展示或融合误读。

## 建议处理顺序

1. 先修F1–F3：失败结果不发布，版本哈希准确，上下游状态与产物对应。
2. 接人口前落实U1：覆盖与分配分开，输出全网去重范围。
3. 做可点击溯源和Coze接入前落实U2及机器可读语义字段。
4. 同时补运行环境锁定、质量报告与显示精度。以上不会要求推翻现有英制半径或更换当前空间计算方法。
