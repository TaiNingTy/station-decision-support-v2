# 第 11 步 · 让 AI 智能体读取 GIS 数据（2026-09-20）

## 起因与方向修正

第 10 步的设计里，"识别"全部在数据管线里由代码完成，智能体只读一张提炼好的事实表。业主指出这偏离了我们讨论的 V2：**用 AI 智能体去做 GIS 数据的读取非常重要**。业主同时确定三点：热力图用公开数据推算的街区活动强度生成栅格和图片，明确标为代理而非实测；G2 同时拿图片和格值表；热力图与 zoning 结合着读，作为辅助而不是决定性数据。

原则因此改为：**AI 读取与判读，代码核验，人决定。**

## 做了什么

1. **采集**：县 GIS 的地块多边形、现状用地、铁路、Metrorail 线；2020 年普查街区人口。按 id 分块取数并核对条数；含业主姓名的房产记录层不取，地块层不请求地址与法律描述。校验 PASS。
2. **阶段 `gis_objects`**：21 站 8,982 个带 id 的要素（道路分组、铁路、既有导轨、zoning 多边形、现状用地类别、地块、热度栅格、街区组）加代码汇总数字；热度代理 453 格；角色提示 2,619 条，不给智能体看。已接入登记表、编排器、就绪视图与回归（`gis_objects_stage`）。
3. **导出**：每站 G1、G2 输入、热度代理图与简报，镜像到 `docs/gis/` 供 HTTP 节点拉取；图片字节稳定。
4. **知识库 kb-v2.1**：新增 GIS 读取指引与由图层自身生成的图例。
5. **Coze 设计**：读取智能体 G1（道路、铁路与导轨、zoning、现状用地、地块）与 G2（热度代理图 + 格值表、街区组、zoning）；代码节点 `gis_gate.js`、`gis_verify.js`；输出闸门带上经核验的空间证据；下游三个智能体接收"空间证据摘要"并被告知它只是辅助。设计文档与中文搭建手册已重写。
6. **校验器**：Python 校验器核对空间证据里的每个要素 id 与汇总数字 id，并报告 G1 的角色判读与规则提示的一致率和分歧清单。

## 构建中发现并处理的问题

- **县"铁路"图层的语义陷阱**：图层无属性，窗口内约 41% 的"铁路"其实是 Metromover 导轨、27% 是 Metrorail。若照单全收，待转换的设施会被读成障碍。已按几何拆分（先导轨、再 Metrorail、余下为其他铁路；约 2.0 mi 同时靠近两条线的轨道按此顺序归入导轨，所以"靠近 Metrorail 8.94 mi"与拆分后的 6.92 mi 是两个口径），并在核验节点里写成硬检查。
- **热度代理的方法局限**：数值按街区陆地均摊，公园所在的格子显示偏热。已写进配置、图片说明与知识库，并要求 G2 把热格与 zoning、现状用地一起读，标出"均摊造成的假热格"。
- **图例的诚实边界**：Miami 21 官方术语表只核实到 FLR 的定义；R / L / O 等字母的含义未能从可直接读取的官方页面核实，图例写明"未核实，只能当标签"，不凭记忆填写。
- **地块用途分组**：初版有 22 种描述前缀未归组，已依据图层自带文字补全；"市中心的蔬菜耕地"这类税务分类异常原样保留。
- **地块行数上限**：每站最多列 150 个地块（按距离），其余只进分组汇总；有的站被截掉三四百个，已在汇总数字里如实报告。

## 验证

- `node coze/v2/evals/run.js`：32/32（GIS 闸门 4、GIS 核验 10、输入闸门 6、输出闸门 12）。
- 端到端一致性：示例读取结果经 JS 核验 VALID、JS 输出闸门 VALID、Python 校验器 PASS；一致率报告 7/7，另提示一个带障碍提示的水域类别未被读到。示例均为手写的格式示例，不是模型输出。
- 回归：[regression_results.json](regression_results.json)，28 个场景 / 302 项检查全部通过，含新增的 `gis_objects_stage`（15 项：阶段 DONE、校验 PASS、21 站齐全、id 唯一、zoning 裁剪与空间连接包一致、地块无业主与地址字段、热度标为代理、街区人口全部匹配、铁路图层三分、Bayfront Park 的导轨是设施而非铁路、提示不给智能体、热度与 zoning 联读的汇总数字存在、消费三个包、就绪视图 DONE、与已发布包逐字节一致）。对象数 8,982 与提示数 2,619 已在全量重建后的当前包里复核。
- zoning 裁剪与空间连接包逐区偏差为零；热度图两次生成字节一致。
