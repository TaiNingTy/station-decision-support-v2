# 第 5 步 · 服务基线与低／中／高情景（2026-09-15）

依据规则文档 规则 5 与已定决策（基数取全方式通勤出行；采用率为占全方式出行的份额；现状公交分担率只作低档参考上限；枢纽流入不建模；返程镜像；单一峰值参数），字段契约 §8、§9、§10。

## 两个新阶段

| 阶段 | 脚本 | 内容 |
|---|---|---|
| `service_baseline` | `scripts/build_miami_service_baseline.py` | GTFS 快照工作日服务（日历 service 11，周一至周五，无例外）按 stop → 站点映射汇总到 21 站：逐小时、逐线路的排定出发次数，首末班，五个时段的每小时出发次数与隐含班距。12,307 条工作日 stop_times 全部对上站点。`data_nature: administrative_record`；排定不等于运营，出发次数不是容量也不是客流。进入输入包后 `service_baseline` 的获取状态为 `derived`（枚举新增） |
| `scenarios` | `scripts/build_miami_scenarios.py` | 按计算链逐步计算三档情景，每步一个参数，每个参数带三组标记；结果 `data_nature: model_output`，未校准；manifest 带 `assumption_parameter_ids` |

编排器现为 站点主表 → 空间连接 → 人口层 → 就业层 → 服务基线 → 输入包 → 情景 → readiness 校验。登记表新增 `service_baseline`（配置输入，不是 AI 解读的必需层）。

## 计算链与参数

| 步 | 参数 | 类别 | 值 | 来源 |
|---|---|---|---|---|
| 1 基数 | 两端都在全网 ½ mile 并集内的主要岗位联系 P01，按两端街区的覆盖份额计入（2026-09-17 评测后修正；整块纳入的上限为 9,706） | 推算，行政数据建模 × 陆地份额约定 | 8,815 | 就业层 OD 汇总 both_in_coverage_weighted JT01 |
| 2 通勤出行 | 在家办公比例 P02；到岗率 A01 | 推算；假设 | 27.3%；0.85 | 人口层全网去重 R02；假设 |
| 3 全目的出行 | 非通勤出行 ÷ 通勤出行 A02 | 假设，三档 | 0.5 / 1.0 / 1.5 | NHTS 只作说明，迁移系数未观测 |
| 4 高峰小时 | 单一峰值份额 P05 | 推算，依赖假设 A07 | 35.5%（8:00–8:59） | B08302 最高 60 分钟窗口；Metromover 分时客流未取得 |
| 5 PRT 出行 | 采用率 A03 | 假设，三档 | 0.05 / 0.15 / 0.30 | 低档不超过观测公交分担率 6.1%（P06，只作参照） |
| 6 分站上下客 | 分配规则 A04、方向与返程 A05、非通勤模式 A06 | 假设 | 按候选站点陆地份额归一，PM 镜像 | 守恒检查通过 |

三档只改 A02 与 A03，其余参数共用。结果（覆盖份额修正后）：早高峰网内 PRT 出行量 低 145 / 中 580 / 高 1,449 人次；分站上下客在 `station_scenario_table.json`，每站附排定出发次数作观测参照，不作容量比较。

**成果含义限制**：基数只含网内两端的联系，不含一端在网外的约 17.8 万份工作地联系、居民在州外的岗位与枢纽换乘流入；数值是不含区域流入的下限量级，是演示计算链的模型输出，不是需求预测，也未与实测客流校准。

## 就绪状态

`ready_for_ai_interpretation: true`；`config_inputs_complete: false`，缺站台可建设空间与车辆参数两项；`config_assumption_backed_inputs: ["scenario_results"]`。服务基线已从"可由 GTFS 推算"变为有值。

## 验证

[regression_results.json](regression_results.json)：21 个场景全部在临时副本中运行。本步新增 `service_baseline_and_scenarios`（15 项）：两阶段 DONE 且校验 PASS；每档守恒；低 ≤ 中 ≤ 高；低档采用率不超过观测公交分担率；manifest 含假设 ID；共用参数全部带类别标记；情景阶段消费输入包、就业层与服务基线；readiness 把情景结果列为假设支撑、缺失只剩两项；两阶段的包与本目录已发布的包逐字节一致。`input_package_build` 增加"服务基线字段为 derived 且有值"的检查。

首次运行时四个包的"与已发布包逐字节一致"检查失败，原因是本步修改了聚合器脚本，而各层 manifest 的 `code` 登记了它的哈希；按"代码变化只提示不过期"的规则重发全部包后通过。这正是登记代码依赖的用意：产物不变时包 ID 仍能反映代码版本。
